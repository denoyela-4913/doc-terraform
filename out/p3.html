Providers, ressources, dépendances

Terraform ne sait rien faire seul : ce sont les providers qui parlent aux plateformes. Tu déclares leurs versions, tu décris des resources, tu lis des data sources, et Terraform déduit l'ordre grâce aux dépendances.

Objectifs
  • Déclarer un provider avec required_providers et une contrainte de version.
  • Distinguer resource et data, et lire leurs attributs.
  • Prédire l'ordre de création et comprendre un remplacement en cascade.

3.1 Déclarer ses providers

terraform {
  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
  }
}
  • Clé (local) : le nom local du provider dans ce module.
  • source : adresse globale [HOSTNAME/]NAMESPACE/TYPE. Sans hostname, c'est registry.terraform.io : hashicorp/http est un raccourci de registry.terraform.io/hashicorp/http.
  • version : une contrainte, facultative mais fortement recommandée. La doc conseille ~> dans un module racine, >= dans un module réutilisable.

Un bloc provider "nom" { … } sert ensuite à configurer le provider (authentification, région…). Certains, comme random et local, n'ont rien à configurer.

Lire une contrainte de version

OpérateurSens
= (ou rien)une seule version exacte (ne se combine pas)
!=exclut une version exacte
> >= / < <=plus récent / plus ancien que la version donnée
~>seul le composant le plus à droite peut augmenter

On combine avec des virgules dans une même chaîne : version = ">= 1.2.0, < 2.0.0".

Le fichier de verrouillage

Après init, les versions réellement choisies sont enregistrées dans .terraform.lock.hcl. La doc recommande de le committer : tout le monde (et la CI) obtient alors les mêmes versions. Pour monter de version, change la contrainte puis relance terraform init (ou init -upgrade).

developer.hashicorp.com/terraform/language/providers/requirements · /cli/commands/init

3.2 Resource : créer et gérer

resource "local_file" "salut" {     # TYPE + LABEL
  filename = "${path.module}/salut.txt"   # arguments : propres au provider
  content  = "Serveur : ${random_pet.serveur.id}\n"
}

La doc : « Terraform utilise ce label pour suivre la ressource dans ton state ». Les arguments dépendent du provider : cherche-les dans sa documentation (Terraform Registry). Les méta-arguments valables sur toute ressource sont count, for_each, depends_on, provider et le bloc lifecycle (partie 5).

3.3 Data source : lire sans toucher

data "local_file" "relu" {
  filename = local_file.salut.filename
}
# se lit : data.local_file.relu.content

« Les data sources récupèrent des données du provider mais ne créent ni ne modifient aucune ressource. » Terraform essaie de les lire pendant le plan. Si un argument dépend d'une ressource qui va changer, la lecture est reportée à l'apply : le plan affiche alors « will be read during apply » (observé dans le TD).

Piège

Changer un argument qui force un remplacement (# forces replacement, symbole -/+) détruit puis recrée la ressource, et entraîne ses dépendants. C'est ce que tu observes dans le TD avec -replace.

TD 3

Ordre, data source et remplacement en cascade

≈ 25 min · aucun compte cloud
  1. Crée le projet. Dans un dossier td3, écris ce main.tf. 
    terraform {
  required_providers {
    random = {
      source  = "hashicorp/random"
      version = "~> 3.6"
    }
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
  }
}

resource "random_pet" "serveur" {
  length = 2
}

resource "local_file" "salut" {
  filename = "${path.module}/salut.txt"
  content  = "Serveur : ${random_pet.serveur.id}\n"
}

data "local_file" "relu" {
  filename = local_file.salut.filename
}

output "contenu_relu" {
  value = data.local_file.relu.content
}

    $ terraform init
$ grep -A2 'hashicorp/random' .terraform.lock.hcl

    Le lock file indique la version précise choisie (chez moi 3.9.1 pour la contrainte ~> 3.6).

  2. Planifie et repère la data source différée. 
    $ terraform plan

      # data.local_file.relu will be read during apply
  # (depends on a resource or a module with changes pending)
  # local_file.salut will be created
  # random_pet.serveur will be created
Plan: 2 to add, 0 to change, 0 to destroy.

    Question : pourquoi la data source n'est-elle pas lue tout de suite ? Parce que local_file.salut n'existe pas encore.

  3. Applique et lis la sortie. 
    $ terraform apply -auto-approve
$ terraform output contenu_relu

    Tu retrouves « Serveur : <nom-aléatoire> ». La data source a bien relu le fichier créé juste avant.

  4. Affiche le graphe. 
    $ terraform graph

    Cherche les lignes avec -> : "data.local_file.relu" -> "local_file.salut" et "local_file.salut" -> "random_pet.serveur". En option, si tu installes Graphviz (sudo apt install graphviz) : terraform graph | dot -Tpng > graphe.png.

  5. Force un remplacement et mesure la cascade. 
    $ terraform plan -replace=random_pet.serveur

      # data.local_file.relu will be read during apply
  # local_file.salut must be replaced
  # random_pet.serveur will be replaced, as requested
Plan: 2 to add, 0 to change, 2 to destroy.

    Tu n'as demandé que random_pet, mais local_file est remplacé aussi puisque son contenu en dépend. Nettoie avec terraform destroy.

Pour aller plus loin

Change version = "~> 3.6" en version = "~> 99.0" puis relance terraform init : l'erreur te montre comment une contrainte impossible est refusée. Remets la bonne valeur ensuite.
