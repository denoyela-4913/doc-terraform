Variables, locals, outputs

Une configuration utile se paramètre. Les variables entrent, les locals calculent, les outputs sortent. Et chaque valeur a une source, avec un ordre de priorité à connaître.

Objectifs
  • Déclarer des variables typées, documentées et validées.
  • Prédire quelle valeur gagne quand plusieurs sources existent.
  • Utiliser locals à bon escient et lire/protéger des output.

4.1 Déclarer une variable

variable "environnement" {
  type        = string
  description = "Environnement cible"
  default     = "dev"

  validation {
    condition     = contains(["dev", "staging", "prod"], var.environnement)
    error_message = "L'environnement doit etre dev, staging ou prod."
  }
}
ArgumentRôle
typele type attendu (string, number, list(string), map(object({…}))…)
defaultvaleur de secours. Sans default, Terraform demande la valeur avant le plan
descriptionexplique la variable aux utilisateurs du module
validationun bloc avec condition et error_message
sensitivemasque la valeur dans la sortie CLI (mais elle reste dans le state !)
nullable · ephemeralephemeral : la valeur n'est écrite ni dans le state ni dans le plan

4.3 Locals : nommer un calcul

locals {
  prefixe  = "app-${var.environnement}"
  est_prod = var.environnement == "prod"
}
# se lit avec le mot SINGULIER :  local.prefixe

La doc les recommande quand tu réutilises une valeur à plusieurs endroits ou quand l'expression est complexe. Elle prévient aussi : les locals « peuvent rendre la configuration plus difficile à lire car ils masquent l'origine des valeurs ». Ils ne sont visibles que dans leur module.

4.4 Outputs : exposer des valeurs

output "prefixe" {
  description = "Prefixe calcule"
  value       = local.prefixe
}

output "secret_affiche" {
  value     = var.mot_de_passe
  sensitive = true
}

Après un apply, les sorties du module racine s'affichent. Un module parent lit celles d'un module enfant avec module.NOM.SORTIE.

Sensitive ≠ secret protégé
  • sensitive = true masque la valeur dans la sortie CLI : (sensitive value) dans le plan, <sensitive> avec terraform output.
  • Mais la valeur reste dans le state et les fichiers de plan : « quiconque y accède accède à tes valeurs sensibles ».
  • Observé en 1.17.0 : terraform output secret_affiche, -raw et -json l'affichent en clair.

TD 4

Valider, prioriser, masquer

≈ 25 min · aucun compte cloud
  1. Écris la configuration. Dans un dossier td4 : 
    terraform {
  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
  }
}

variable "environnement" {
  type        = string
  description = "Environnement cible"
  default     = "dev"

  validation {
    condition     = contains(["dev", "staging", "prod"], var.environnement)
    error_message = "L'environnement doit etre dev, staging ou prod."
  }
}

variable "mot_de_passe" {
  type        = string
  description = "Un secret de demonstration"
  default     = "abc123"
  sensitive   = true
}

locals {
  prefixe  = "app-${var.environnement}"
  est_prod = var.environnement == "prod"
}

resource "local_file" "conf" {
  filename = "${path.module}/${local.prefixe}.conf"
  content  = "mode=${local.est_prod ? "strict" : "souple"}\nsecret=${var.mot_de_passe}\n"
}

output "prefixe" {
  description = "Prefixe calcule"
  value       = local.prefixe
}

output "secret_affiche" {
  description = "Le secret (masque)"
  value       = var.mot_de_passe
  sensitive   = true
}

    $ terraform init
  2. Déclenche la validation. 
    $ terraform plan -var environnement=test

    Error: Invalid value for variable

  on main.tf line 10:
  10: variable "environnement" {
    │ var.environnement is "test"

L'environnement doit etre dev, staging ou prod.

    Ton error_message s'affiche tel quel. Puis applique avec les valeurs par défaut : terraform apply -auto-approve. Le fichier app-dev.conf apparaît.

  3. Joue avec la précédence. Observe la sortie prefixe après chaque apply. 
    $ TF_VAR_environnement=staging terraform apply -auto-approve   # env > default
$ echo 'environnement = "prod"' > terraform.tfvars
$ TF_VAR_environnement=staging terraform apply -auto-approve   # tfvars > env
$ TF_VAR_environnement=staging terraform apply -auto-approve -var environnement=dev   # -var > tout

    prefixe = "app-staging"
prefixe = "app-prod"
prefixe = "app-dev"

    Tu viens de vérifier l'escalier : -var > terraform.tfvars > TF_VAR_ > default.

  4. Découvre ce que « sensitive » masque vraiment. 
    $ terraform output
$ terraform output secret_affiche
$ grep -c abc123 terraform.tfstate

    prefixe = "app-dev"
secret_affiche = <sensitive>
"abc123"
1

    Masqué dans la liste, lisible par nom, et présent dans le state. Garde ce réflexe pour la partie 8.

  5. Mesure l'effet d'un secret dans un plan. 
    $ terraform plan -var mot_de_passe=autre

    Cherche content = (sensitive value) # forces replacement : le contenu du fichier est masqué, mais Terraform sait qu'il change. Nettoie : rm terraform.tfvars && terraform destroy -auto-approve.
