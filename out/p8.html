Pro : sécurité, CI, projet final

Ce qui sépare un TP d'un usage en équipe : protéger les secrets, automatiser sans surprise, déboguer, savoir ce qu'on ne fait pas. Puis tu mets tout ensemble avec un vrai conteneur.

Objectifs
  • Savoir où vivent les secrets et comment limiter les dégâts.
  • Construire une chaîne d'automatisation sûre : fmt → validate → plan -out → apply.
  • Déboguer avec TF_LOG, reconnaître les mauvaises pratiques (-target, provisioners).
  • Déployer un conteneur nginx avec Docker de bout en bout.

8.1 Secrets et state

Ce que sensitive ne fait pasIl masque la valeur à l'écran. Elle reste dans le state et les fichiers de plan. Le state local est stocké « dans un fichier en clair », qui inclut les valeurs secrètes que tu as définies.
Ce que la doc recommandeStocker le state à distance, le chiffrer au repos, restreindre l'accès, journaliser les accès. Et utiliser les valeurs éphémères quand c'est possible.
  • ephemeral (variables et sorties de modules enfants, Terraform 1.10+) et les arguments write-only (1.11+) ne sont écrits ni dans le state ni dans le plan. Combine ephemeral et sensitive pour aussi masquer à l'écran.
  • random_password traite son résultat comme sensible, mais il est stocké dans le state : la doc du provider recommande la variante éphémère pour les arguments write-only.
  • Ne mets jamais d'identifiants dans la configuration (ni dans le bloc backend) : ils finissent dans le state et les plans.

8.2 Automatiser sans surprise

Option / variableÀ savoir (doc officielle)
plan -out=FICHIER puis apply FICHIERL'apply applique « exactement » le plan sauvegardé ; -auto-approve est ignoré (le fichier vaut approbation) et aucun autre mode ou option de planification n'est accepté.
apply -auto-approveSaute la confirmation, y compris pour des destructions. En automatisation, planifie et relis d'abord.
-detailed-exitcode0 pas de changement · 1 erreur · 2 succès avec changements.
-target=ADRESSERéservé aux cas exceptionnels (réparer une erreur, contourner une limite). En routine, risque de dérive non détectée.
-lock=false / -lock-timeout=3sDésactiver le verrou est dangereux si d'autres lancent des commandes sur le même workspace. Préfère attendre avec -lock-timeout.
-parallelism=nLimite les opérations concurrentes (10 par défaut).
TF_IN_AUTOMATION · TF_INPUT=falseCosmétique (plus de suggestions de commandes) · ne jamais demander de saisie.
TF_CLI_ARGS · TF_CLI_ARGS_planAjoute des arguments à toutes les commandes, ou à une seule.
terraform fmt -check -recursive
terraform validate
terraform plan -out=tfplan -detailed-exitcode
code=$?
if [ "$code" -eq 1 ]; then echo "erreur de plan"; exit 1; fi
if [ "$code" -eq 2 ]; then echo "des changements sont prevus : relecture humaine requise"; fi
# apres approbation :
terraform apply tfplan

8.3 Déboguer

  • TF_LOG prend un niveau : TRACE (le plus verbeux), DEBUG, INFO, WARN, ERROR. Les logs vont sur stderr.
  • TF_LOG_PATH=fichier les ajoute à un fichier, mais TF_LOG doit aussi être défini. TF_LOG_CORE et TF_LOG_PROVIDER séparent le cœur et les providers.
  • Pour désactiver : unset TF_LOG ou TF_LOG=off.
$ TF_LOG=INFO TF_LOG_PATH=/tmp/tf.log terraform plan
$ head -2 /tmp/tf.log

2026-10-28T22:34:15.615+0100 [INFO]  Terraform version: 1.17.1
2026-10-28T22:34:15.615+0100 [INFO]  Go runtime version: go1.26.10
Prudence

Les logs détaillés peuvent contenir des valeurs de ta configuration. Ne les publie pas tels quels. La doc précise aussi que le format TF_LOG=JSON n'est pas une interface stable.

8.4 Provisioners : en dernier recours

La doc est nette : Terraform est conçu pour l'infrastructure immuable, et « tu dois épuiser toutes les alternatives avant d'utiliser des provisioners ». Elle conseille d'abord la documentation du provider, une demande de fonctionnalité, ou une image/gestion de configuration. Si tu en as vraiment besoin :

resource "terraform_data" "bonjour" {
  provisioner "local-exec" {
    command = "echo bonjour depuis un provisioner > provisioner.txt"
  }
}
  • Un provisioner qui échoue fait échouer l'apply (on_failure = continue pour ignorer).
  • when = destroy l'exécute avant la destruction ; s'il échoue, il sera rejoué au prochain apply : écris-le idempotent.
  • terraform_data permet d'en lancer sans les lier à une ressource précise.

8.5 Que mettre dans Git ?

À versionner*.tf, .terraform.lock.hcl (recommandé par la doc), tests *.tftest.hcl, README.
À ne pas versionner.terraform/ (providers téléchargés), terraform.tfstate et .backup (secrets possibles), fichiers de plan, *.tfvars contenant des secrets.

La doc state et init recommandent de versionner le lock file et de ne pas versionner le state. Le détail du .gitignore est une convention courante.

TD 8

Projet final : un site nginx avec Docker

≈ 35 min · Docker requis

Tu déploies un conteneur nginx, tu changes son port, tu valides tes entrées et tu nettoies. Prérequis : Docker qui tourne, ton utilisateur autorisé à l'utiliser, et le port 8000 libre. Le provider est kreuzwerker/docker (celui du tutoriel officiel).

  1. Écris le projet. Dans un dossier td8 : 
    terraform {
  required_providers {
    docker = {
      source  = "kreuzwerker/docker"
      version = "~> 4.2.0"
    }
  }
}

provider "docker" {}

variable "port_externe" {
  type        = number
  description = "Port local expose par nginx"
  default     = 8000

  validation {
    condition     = var.port_externe >= 1024 && var.port_externe <= 65535
    error_message = "Choisis un port entre 1024 et 65535."
  }
}

resource "docker_image" "nginx" {
  name         = "nginx:latest"
  keep_locally = false
}

resource "docker_container" "nginx" {
  image = docker_image.nginx.image_id
  name  = "tutorial"

  ports {
    internal = 80
    external = var.port_externe
  }
}

output "url" {
  description = "Adresse du site"
  value       = "http://localhost:${var.port_externe}"
}

    $ terraform init
$ terraform fmt -check
$ terraform validate

    Attendu : le provider kreuzwerker/docker v4.2.x s'installe, puis « The configuration is valid ».

  2. Planifie dans un fichier, puis applique ce plan. 
    $ terraform plan -out=tfplan -detailed-exitcode ; echo "code : $?"
$ terraform apply tfplan

    Le code de retour du plan est 2 (changements à appliquer). L'apply se termine par « Apply complete! Resources: 2 added » et affiche url = "http://localhost:8000".

  3. Vérifie que ça tourne vraiment. 
    $ curl -s localhost:8000 | grep -o "<title>.*</title>"
$ docker ps --format '{{.Names}}  {{.Ports}}' | grep tutorial
$ terraform plan -detailed-exitcode ; echo "code : $?"

    <title>Welcome to nginx!</title>
tutorial  0.0.0.0:8000->80/tcp
code : 0

    Un second plan renvoie 0 : l'infrastructure correspond à la configuration.

  4. Change le port et valide tes entrées. 
    $ terraform plan -var port_externe=80
$ terraform plan -var port_externe=8080
$ terraform apply -auto-approve -var port_externe=8080
$ curl -s -o /dev/null -w "%{http_code}\n" localhost:8080

    Error: Invalid value for variable
Choisis un port entre 1024 et 65535.

  # docker_container.nginx must be replaced
          ~ external = 8000 -> 8080 # forces replacement
Plan: 1 to add, 0 to change, 1 to destroy.

200

    Le port 80 est refusé par ta validation. Le changement de port force le remplacement du conteneur (-/+). Le site répond sur 8080 et plus sur 8000.

  5. Active les logs, puis détruis proprement. 
    $ TF_LOG=INFO TF_LOG_PATH=/tmp/tf.log terraform plan -var port_externe=8080
$ head -2 /tmp/tf.log
$ terraform destroy -auto-approve -var port_externe=8080
$ docker ps -a --format '{{.Names}}' | grep -c tutorial

    Attendu : « Destroy complete! Resources: 2 destroyed. » et le dernier compte vaut 0 : plus de conteneur tutorial. Terraform a tout nettoyé, c'est le but.

Défis pour continuer
  • Ajoute un second conteneur avec for_each sur une map { web = 8000, api = 8001 } (attention à l'attribut name, unique par conteneur).
  • Passe le code dans un module modules/site avec une variable port et un output url.
  • Écris un .tftest.hcl avec command = plan qui vérifie que output.url vaut http://localhost:8000.
