Pièges et astuces

Ce qu'il vaut mieux ne pas faire, et le bon réflexe à la place. Chaque conseil est rattaché à la doc officielle ou à une expérience réelle.

Les 10 pièges classiques

PiègeUtiliser count sur une liste qui change : retirer un élément du milieu décale les indices.
RéflexeUtiliser for_each sur un set ou une map. Observé : avec count, retirer bob remplace [1] et détruit [2] ; avec for_each, seul bob part.
PiègePrendre sensitive = true pour un coffre-fort.
RéflexeC'est un masque d'affichage. La valeur reste dans le state et les plans. Chiffre et restreins le state, et préfère les valeurs ephemeral. Observé : terraform output NOM la montre en clair.
PiègeRenommer une ressource dans le code sans moved.
RéflexeAjoute moved { from = … to = … } : le plan affiche « has moved to ». Observé : sans lui, « 2 to add, 2 to destroy ». Garde les blocs moved (les retirer est cassant).
PiègeUtiliser -target en routine.
RéflexeRéserve-le aux cas exceptionnels (réparer, contourner une limite). La doc avertit d'une dérive non détectée.
PiègeÉditer terraform.tfstate à la main, ou le committer dans Git.
RéflexePasse par terraform state. Stocke le state dans un backend distant, chiffré, avec verrou et contrôle d'accès.
PiègeAjouter depends_on « pour être sûr ».
RéflexeRéférence un attribut : la dépendance est alors implicite. depends_on est un dernier recours, il rend les plans plus conservateurs.
PiègeUtiliser les workspaces pour isoler dev et prod.
RéflexeLa doc : ils partagent le même backend, ce n'est pas une isolation adaptée. Sépare configurations et backends.
PiègeMettre des variables ou des identifiants dans le bloc backend.
RéflexeLe bloc backend n'accepte ni variables ni locals. Passe les valeurs avec -backend-config et les identifiants via l'environnement.
Piègeapply -auto-approve sans avoir relu le plan, ou -lock=false.
RéflexePlanifie dans un fichier (-out), relis, applique ce fichier. Attends le verrou avec -lock-timeout.
PiègeNe pas committer .terraform.lock.hcl.
RéflexeLa doc le recommande : toute l'équipe et la CI obtiennent les mêmes versions de providers.

Les astuces qui font gagner du temps

Console

terraform console pour tester une fonction ou une expression sans rien déployer. En script : echo 'upper("a")' | terraform console.

Formater d'un coup

terraform fmt -recursive corrige tout le dépôt ; fmt -check sert de garde dans la CI.

Plan sauvegardé

plan -out=tfplan puis apply tfplan : tu appliques exactement ce que tu as relu.

Scripter sans lire le state

terraform output -json et terraform show -json plutôt que d'analyser le fichier.

Variable d'environnement

export TF_VAR_environnement=staging : pratique en CI, mais la source la plus faible avant default.

Remplacer une ressource

plan -replace=ADRESSE force le remplacement d'une instance. Observé : ses dépendants sont remplacés aussi.

Détecter la dérive

plan -refresh-only montre ce qui a changé hors de Terraform sans rien défaire.

Voir le graphe

terraform graph | dot -Tpng > graphe.png (nécessite Graphviz) pour comprendre l'ordre des opérations.

Cache des providers

TF_PLUGIN_CACHE_DIR évite de retélécharger les mêmes providers dans chaque dossier de TD.

Journaux ciblés

TF_LOG_PROVIDER ou TF_LOG_CORE pour ne voir que les logs d'un côté ; TF_LOG_PATH exige que TF_LOG soit défini.

Check-list avant de partager ton code

Avant un commit
  • terraform fmt -recursive puis terraform validate.
  • Chaque variable et output a un type et une description.
  • Les secrets ont sensitive = true et ne sont pas dans les fichiers versionnés.
  • Les versions de providers sont contraintes (~>) et .terraform.lock.hcl est committé.
  • Pas de terraform.tfstate, pas de .terraform/, pas de fichier de plan dans Git.
  • Un plan a été relu avant tout apply en environnement partagé.
