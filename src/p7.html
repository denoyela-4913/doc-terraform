Modules et qualité

Quand tu recopies un bloc, c'est qu'il faut un module. Puis tu gardes ton code propre avec le formatage, la validation et les tests.

Objectifs
  • Écrire et appeler un module local (variables en entrée, outputs en sortie).
  • Passer un module à for_each et refactorer sans détruire.
  • Appliquer les conventions de style, fmt, validate et écrire un test .tftest.hcl.

7.1 Qu'est-ce qu'un module ?

Un module est « une collection de ressources que Terraform gère ensemble ». Le répertoire racine de ton workspace est le root module ; les modules qu'il appelle via des blocs module sont des child modules. Le même module peut être appelé plusieurs fois, et un module peut en appeler d'autres.

Le conseil de la doc

Quand tu provisionnes à répétition des ensembles de ressources similaires, « écris des modules réutilisables pour les codifier ». Les modules peuvent venir du système de fichiers local, d'un registre Terraform (public ou privé) ou d'un dépôt VCS.

developer.hashicorp.com/terraform/language/modules

7.2 Écrire et appeler un module

terraform {
  required_providers {
    local = {
      source = "hashicorp/local"
    }
  }
}

resource "local_file" "message" {
  filename = "${var.dossier}/${lower(var.nom)}.txt"
  content  = "Salut ${var.nom} !\n"
}

module "alice" {
  source  = "./modules/salutation"
  nom     = "Alice"
  dossier = "${path.module}/out"
}

Après avoir ajouté ou modifié un module, relance terraform init : il installe les modules enfants (« Initializing modules… »). Dans le state, les ressources d'un module ont une adresse préfixée : module.alice.local_file.message.

7.3 Les conventions de la doc

FichierContenu conseillé
terraform.tfun seul bloc terraform avec required_version et required_providers
providers.tftous les blocs provider
backend.tfla configuration du backend
main.tfressources et data sources
variables.tf · outputs.tfvariables · outputs, en ordre alphabétique
locals.tflocals partagés entre fichiers (sinon en haut du fichier qui les utilise)
À faire
  • 2 espaces par niveau, = alignés
  • count / for_each en premier, puis les arguments, les blocs, lifecycle, depends_on à la fin
  • type et description sur chaque variable et output
  • sensitive = true pour mots de passe et clés
  • noms en noms descriptifs avec underscores
À éviter
  • répéter le type dans le nom (local_file "local_file_1")
  • commentaires // et /* */
  • abuser de variables et de locals
  • validation partout : seulement si les valeurs ont des contraintes strictes

7.4 fmt, validate, test

OutilCe qu'il apporte
terraform fmtReformate au style canonique. -recursive descend dans les sous-dossiers, -check vérifie sans écrire (code 0 si tout est formaté, non nul sinon), -diff montre les changements.
terraform validateSyntaxe et cohérence interne (noms d'attributs, types), sans variables ni services distants. À lancer après init (ou init -backend=false).
terraform testFichiers .tftest.hcl : blocs run (command = plan ou apply, apply par défaut) avec des assert (condition + error_message).
run "chemins_attendus" {
  command = plan            # pas d'infrastructure créée : comme un test unitaire

  assert {
    condition     = output.chemins["alice"] == "./out/alice.txt"
    error_message = "Le chemin d'alice est inattendu."
  }
}
Astuce

Dans la CI, enchaîne terraform fmt -check → terraform validate → terraform test. La doc de style conseille aussi un linter comme TFLint pour les règles propres à ton organisation.

TD 7

Ton premier module, puis for_each, fmt et test

≈ 30 min · aucun compte cloud
  1. Crée le module. Dans un dossier td7 : 
    $ mkdir -p modules/salutation

    variable "nom" {
  type        = string
  description = "Personne a saluer"
}

variable "dossier" {
  type        = string
  description = "Dossier de sortie"
}

    terraform {
  required_providers {
    local = {
      source = "hashicorp/local"
    }
  }
}

resource "local_file" "message" {
  filename = "${var.dossier}/${lower(var.nom)}.txt"
  content  = "Salut ${var.nom} !\n"
}

    output "chemin" {
  description = "Chemin du fichier cree"
  value       = local_file.message.filename
}
  2. Appelle-le deux fois. 
    terraform {
  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
  }
}

module "alice" {
  source  = "./modules/salutation"
  nom     = "Alice"
  dossier = "${path.module}/out"
}

module "bob" {
  source  = "./modules/salutation"
  nom     = "Bob"
  dossier = "${path.module}/out"
}

output "chemins" {
  value = [module.alice.chemin, module.bob.chemin]
}

    $ terraform init
$ terraform apply -auto-approve
$ terraform state list

    Initializing modules...
- alice in modules/salutation
- bob in modules/salutation
...
chemins = [
  "./out/alice.txt",
  "./out/bob.txt",
]
module.alice.local_file.message
module.bob.local_file.message
  3. Refactore en for_each sans rien détruire. Remplace les deux blocs module et l'output par : 
    module "equipe" {
  for_each = toset(["alice", "bob"])

  source  = "./modules/salutation"
  nom     = title(each.key)
  dossier = "${path.module}/out"
}

moved {
  from = module.alice
  to   = module.equipe["alice"]
}

moved {
  from = module.bob
  to   = module.equipe["bob"]
}

output "chemins" {
  value = [for m in module.equipe : m.chemin]
}

    $ terraform init
$ terraform plan

      # module.alice.local_file.message has moved to module.equipe["alice"].local_file.message
  # module.bob.local_file.message has moved to module.equipe["bob"].local_file.message
Plan: 0 to add, 0 to change, 0 to destroy.

    Les ressources gardent leur existence : elles changent juste d'adresse. Fais terraform apply -auto-approve puis terraform state list.

  4. Formate et valide. Crée un fichier mal formaté, constate, corrige. 
    $ printf 'variable   "x"   {\ntype=string\n    default = "a"\n}\n' > mal.tf
$ terraform fmt -check ; echo "code retour : $?"
$ terraform fmt -diff mal.tf
$ terraform validate

    mal.tf
code retour : 3
--- old/mal.tf
+++ new/mal.tf
@@ -1,4 +1,4 @@
-variable   "x"   {
-type=string
-    default = "a"
+variable "x" {
+  type    = string
+  default = "a"
 }
Success! The configuration is valid.

    Le code de retour non nul (3 ici) liste le fichier fautif : exactement ce qu'une CI exploite. Supprime ensuite mal.tf.

  5. Écris un test. Crée equipe.tftest.hcl : 
    run "deux_fichiers" {
  command = plan

  assert {
    condition     = length(output.chemins) == 2
    error_message = "Il devrait y avoir deux fichiers."
  }
}

    $ terraform test

    equipe.tftest.hcl... in progress
  run "deux_fichiers"... pass
equipe.tftest.hcl... tearing down
equipe.tftest.hcl... pass

Success! 1 passed, 0 failed.

    Casse-le volontairement (== 3) : Terraform affiche un diff et ton error_message. Nettoie avec terraform destroy -auto-approve.

Pour aller plus loin

Ajoute "chloe" à l'ensemble : un seul nouveau fichier est créé, les autres ne bougent pas. C'est tout l'intérêt de for_each sur un module.
