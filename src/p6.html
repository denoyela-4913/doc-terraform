State, backends, refactoring

Le state est la mémoire de Terraform. Le comprendre explique presque tous les comportements surprenants : pourquoi un plan veut recréer quelque chose, pourquoi renommer est dangereux, pourquoi les secrets y traînent.

Objectifs
  • Expliquer le triangle configuration / state / infrastructure réelle.
  • Choisir un backend et connaître les commandes terraform state.
  • Renommer sans détruire (moved), adopter l'existant (import), détecter une dérive.

6.1 Un triangle à trois sommets

6.2 Ce que dit la doc sur le state

  • Par défaut : local, dans terraform.tfstate, avec une sauvegarde terraform.tfstate.backup. Aucune configuration, mais collaboration difficile et perte possible du fichier.
  • Recommandé : HCP Terraform ou un backend distant, avec verrouillage (locking) et contrôle d'accès.
  • Ne jamais l'éditer à la main (utilise terraform state) ni le mettre dans le contrôle de version : il peut contenir des secrets.
  • Pour l'automatisation, préfère terraform output -json et terraform show -json à l'analyse directe du fichier, dont le format peut changer.

Les commandes terraform state

CommandeRôle
state listliste les ressources suivies
state show ADRESSEdétaille une ressource
state mvchange l'adresse d'une ressource dans le state
state rm« oublie » un objet sans le détruire
state pullaffiche le state brut
state replace-providerchange le provider associé

Les commandes qui modifient le state écrivent toujours une sauvegarde (impossible à désactiver) ; les commandes en lecture (list) non.

6.3 Les backends

terraform {
  backend "remote" {
    organization = "example_corp"

    workspaces {
      name = "my-app-prod"
    }
  }
}

Un backend définit où le state est stocké. Par défaut, c'est local. La doc cite : local, remote, azurerm, consul, cos, gcs, http, kubernetes, oci, oss, pg, s3. On ne peut pas en charger d'autres comme des plugins.

Règles à connaître
  • Un seul bloc backend par configuration.
  • Il ne peut référencer ni variables, ni locals, ni data sources.
  • Avec HCP Terraform, on utilise un bloc cloud : il est incompatible avec backend.
  • Pour changer de backend : modifie le bloc, relance terraform init. Terraform propose de migrer le state (-migrate-state) ; -reconfigure l'ignore. Sauvegarde terraform.tfstate d'abord.
  • Évite d'écrire des identifiants dans le bloc : ils seraient écrits en clair dans .terraform et dans les plans. Utilise les variables d'environnement ou les fichiers d'identifiants usuels, et la configuration partielle (-backend-config).

6.4 Refactorer sans casse

moved : renommer ou déplacer

moved {
  from = random_pet.serveur
  to   = random_pet.machine
}

Sans moved, renommer une ressource dans le code revient pour Terraform à « détruire l'ancienne, créer la nouvelle ». Avec lui, le plan affiche has moved to et ne détruit rien (observé dans le TD). Cas d'usage officiels : renommer, passer d'une ressource unique à for_each (to = aws_instance.a["small"]), déplacer dans un module. Garde les blocs moved : les retirer est un changement cassant pour qui utilise ton module.

import : adopter l'existant

Le bloc import rattache un objet qui existe déjà à une adresse de ta configuration. Avec terraform plan -generate-config-out, Terraform peut même écrire le bloc resource correspondant. Détail de syntaxe : le bloc import dans la doc.

refresh-only : constater une dérive

terraform plan -refresh-only produit un plan « dont le seul but est d'aligner le state et les outputs sur les modifications faites hors de Terraform » : il montre la dérive sans rien défaire.

6.5 Les workspaces CLI

Un workspace est « une instance distincte de données d'état à l'intérieur du même répertoire de travail ». Tout répertoire initialisé démarre avec le workspace default. Commandes : terraform workspace list | new | select | delete ; terraform.workspace donne le nom courant.

Ce n'est pas un outil d'isolation

Selon la doc, les workspaces ne sont « pas un mécanisme d'isolation adapté » quand on veut une séparation forte entre déploiements (ex. dev et prod), puisqu'ils partagent le même backend. Ils ne conviennent pas non plus à la décomposition d'un système en sous-systèmes : « chaque sous-système doit avoir sa propre configuration et son propre backend ».

TD 6

Inspecter, renommer, dériver, oublier

≈ 30 min · aucun compte cloud
  1. Crée et applique, puis ouvre le capot. Dans un dossier td6 : 
    terraform {
  required_providers {
    random = {
      source  = "hashicorp/random"
      version = "~> 3.6"
    }
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
  }
}

resource "random_pet" "serveur" {
  length = 2
}

resource "local_file" "salut" {
  filename = "${path.module}/salut-${terraform.workspace}.txt"
  content  = "Serveur : ${random_pet.serveur.id}\n"
}

    $ terraform init && terraform apply -auto-approve
$ terraform state list
$ terraform state show random_pet.serveur
$ head -c 200 terraform.tfstate

    local_file.salut
random_pet.serveur
# random_pet.serveur:
resource "random_pet" "serveur" {
    id        = "flowing-ox"
    length    = 2
    separator = "-"
}
{
  "version": 4,
  "terraform_version": "1.17.1",
  ...

    Le state est un JSON en clair : tu y lis les valeurs de tes ressources. Garde-le à l'esprit pour la partie 8.

  2. Renomme avec moved. Dans main.tf, remplace "serveur" par "machine" (dans le bloc et dans random_pet.serveur.id), puis ajoute à la fin : 
    moved {
  from = random_pet.serveur
  to   = random_pet.machine
}

    $ terraform plan
$ terraform apply -auto-approve
$ terraform state list

      # random_pet.serveur has moved to random_pet.machine
Plan: 0 to add, 0 to change, 0 to destroy.

    Zéro destruction. Essaie ensuite avec un autre nom et sans bloc moved : le plan annonce « Plan: 2 to add, 0 to change, 2 to destroy » (observé), car l'ancienne adresse « is not in configuration ».

  3. Crée une dérive. Modifie le fichier hors de Terraform, puis regarde. 
    $ echo "modifie a la main" > salut-default.txt
$ terraform plan -refresh-only

    Note: Objects have changed outside of Terraform

  # local_file.salut has been deleted
  - resource "local_file" "salut" {
      ...
This is a refresh-only plan, so Terraform will not take any actions to undo

    Pour local_file, un contenu modifié est vu comme « supprimé » (c'est le comportement de ce provider). Répare : terraform apply -auto-approve, puis cat salut-default.txt retrouve « Serveur : … ».

  4. Fais « oublier » une ressource à Terraform. 
    $ terraform state rm local_file.salut
$ terraform state list
$ terraform plan
$ ls salut-default.txt

    Successfully removed 1 resource instance(s).
random_pet.machine
  # local_file.salut will be created
Plan: 1 to add, 0 to change, 0 to destroy.
salut-default.txt

    Le fichier existe encore, mais Terraform ne le connaît plus : il veut le « créer ». Un terraform apply -auto-approve le réadopte.

  5. Essaie un workspace, puis nettoie tout. 
    $ terraform workspace new test
$ terraform apply -auto-approve
$ ls salut-*.txt
$ terraform workspace list
$ terraform destroy -auto-approve
$ terraform workspace select default
$ terraform workspace delete test
$ terraform destroy -auto-approve

    Attendu : deux fichiers (salut-default.txt et salut-test.txt), un state par workspace. Le terraform.workspace dans le nom de fichier évite qu'ils s'écrasent. À la fin, plus aucun salut-*.txt.

Pour aller plus loin

Fais terraform state pull | head -20, puis terraform show -json | head -c 300 : ce sont les sorties que la doc recommande pour scripter plutôt que lire le fichier à la main.
