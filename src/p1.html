Objectifs
  • Expliquer l'infrastructure as code et le rôle de Terraform en une phrase.
  • Enchaîner init, plan, apply, destroy et lire les symboles du plan.
  • Lire un main.tf : bloc terraform, variable, resource, output.

1.1 L'idée

Terraform est, selon sa documentation, « un outil d'infrastructure as code qui permet de construire, modifier et versionner des ressources cloud et on-prem de façon sûre et efficace ». Tu décris l'état voulu dans des fichiers texte ; Terraform calcule comment y arriver.

Dans la doc officielle

Configurations déclaratives : elles décrivent l'état final souhaité. Terraform construit un graphe de ressources et travaille en parallèle sur celles qui sont indépendantes. Les fichiers peuvent être versionnés dans Git, réutilisés et partagés.

developer.hashicorp.com/terraform/intro

1.2 Les commandes du cycle

CommandeCe qu'elle fait (doc officielle)
terraform initInitialise le backend, installe les modules enfants, télécharge les providers. « Sans danger à relancer » : ne supprime jamais configuration ni state.
terraform fmtRéécrit les fichiers au format canonique.
terraform validateVérifie syntaxe et cohérence interne. Ne contacte pas les services distants.
terraform planCompare configuration et infrastructure réelle (state + API du provider). Ne fait aucun changement. Peut sauver le plan dans un fichier.
terraform applyLance un plan, demande confirmation, puis exécute via l'API du provider. Accepte aussi un fichier de plan.
terraform destroySupprime toutes les ressources gérées par le répertoire courant et le workspace sélectionné (après confirmation).

Lire un plan : quatre symboles

+ create~ update in place- destroy-/+ replace

Ce code couleur sert de fil rouge à tout le site : vert = on crée, ambre = on modifie, rouge = on détruit, violet = on remplace (détruire puis recréer).

1.3 Anatomie d'un main.tf

Voici le fichier que tu vas utiliser dans le TD. Il utilise deux providers sans aucun compte cloud : random (génère un nom) et local (écrit un fichier).

terraform {
  required_providers {
    random = {
      source  = "hashicorp/random"
      version = "~> 3.6"
    }
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
  }
}

variable "nom" {
  type        = string
  description = "Nom a saluer"
  default     = "Terraform"
}

resource "random_pet" "serveur" {
  length = 2
}

resource "local_file" "salut" {
  filename = "${path.module}/salut.txt"
  content  = "Bonjour ${var.nom} ! Serveur : ${random_pet.serveur.id}\n"
}

output "chemin" {
  value = local_file.salut.filename
}
À retenir
  • Un bloc resource "TYPE" "LABEL" : le couple TYPE + LABEL est l'identité de la ressource dans le state.
  • On lit un attribut avec TYPE.LABEL.ATTRIBUT (ici random_pet.serveur.id).
  • ${path.module} est le dossier du module où l'expression est écrite.
  • Après init, le dossier contient .terraform/ (providers téléchargés) et .terraform.lock.hcl.
TD 1

Ton premier cycle complet

≈ 20 min · aucun compte cloud

Tout est vérifié avec Terraform 1.17.0. Les noms aléatoires (suitable-tiger) seront différents chez toi.

  1. Prépare le dossier. Crée un dossier vide et colle-y le main.tf ci-dessus. 
    $ mkdir td1 && cd td1
$ nano main.tf        # ou ton éditeur : colle le fichier de la section 1.3
  2. Initialise. Terraform télécharge les deux providers. 
    $ terraform init

    Attendu : « Terraform has been successfully initialized! ». Fais ls -a : tu vois .terraform et .terraform.lock.hcl.

  3. Formate, valide, planifie. Sauve le plan dans un fichier. 
    $ terraform fmt -check
$ terraform validate
$ terraform plan -out=tfplan

      # local_file.salut will be created
  + resource "local_file" "salut" {
      + content              = (known after apply)
      + filename             = "./salut.txt"
      ...
    }

  # random_pet.serveur will be created
  + resource "random_pet" "serveur" {
      + id        = (known after apply)
      + length    = 2
      + separator = "-"
    }

Plan: 2 to add, 0 to change, 0 to destroy.

    Question : pourquoi content est-il « known after apply » ? Parce qu'il dépend de random_pet.serveur.id, qui n'existe pas encore.

  4. Applique le plan sauvegardé, puis observe. 
    $ terraform apply tfplan
$ terraform state list
$ terraform output
$ cat salut.txt

    random_pet.serveur: Creating...
random_pet.serveur: Creation complete after 0s [id=suitable-tiger]
local_file.salut: Creating...
Apply complete! Resources: 2 added, 0 changed, 0 destroyed.

chemin = "./salut.txt"
Bonjour Terraform ! Serveur : suitable-tiger

    Remarque : le random_pet est créé avant le local_file. Le plan sauvegardé s'applique sans te redemander confirmation.

  5. Change une entrée, regarde le symbole, puis détruis. 
    $ terraform plan -var nom=Alex

      # local_file.salut must be replaced
-/+ resource "local_file" "salut" {
      ~ content              = <<-EOT # forces replacement
          - Bonjour Terraform ! Serveur : suitable-tiger
          + Bonjour Alex ! Serveur : suitable-tiger
        EOT
      ...
Plan: 1 to add, 0 to change, 1 to destroy.

    Tu viens de voir un remplacement (-/+) : changer content impose de recréer le fichier. Maintenant nettoie :

    $ terraform destroy

    Tape yes. Résultat attendu : « Destroy complete! Resources: 2 destroyed. »

Pour aller plus loin
  • Relance terraform plan sans rien changer : que dit-il ? (« No changes ».)
  • Applique de nouveau, supprime salut.txt à la main, puis relance plan : Terraform compare avec le réel et planifie de recréer le fichier (« will be created », observé).
